# Technical Plan: CRUD de Pessoas com Next.js e Banco em Memória\n\n## 1. Visão Geral\n\nEste documento descreve a arquitetura técnica e decisões de design para o sistema CRUD de Pessoas desenvolvido com Next.js 14 e banco de dados em memória.\n\n## 2. Arquitetura\n\n### 2.1 Stack Tecnológico\n\n- **Framework**: Next.js 14 (App Router)\n- **Linguagem**: TypeScript 5.3\n- **Runtime**: Node.js 18+\n- **Styling**: CSS Modules\n- **Testing**: Jest + React Testing Library\n- **Package Manager**: npm\n\n### 2.2 Estrutura em Camadas\n\n```\n┌─────────────────────────────────────┐\n│      UI Layer (React Components)    │\n│  - Pages, Forms, Lists, Modals      │\n└──────────────┬──────────────────────┘\n               │\n┌──────────────▼──────────────────────┐\n│    API Layer (Next.js Routes)       │\n│  - Request Handling, Validation     │\n└──────────────┬──────────────────────┘\n               │\n┌──────────────▼──────────────────────┐\n│   Business Logic Layer              │\n│  - Validation, Error Handling       │\n└──────────────┬──────────────────────┘\n               │\n┌──────────────▼──────────────────────┐\n│    Data Layer (In-Memory DB)        │\n│  - CRUD Operations, Indexing        │\n└─────────────────────────────────────┘\n```\n\n## 3. Componentes Principais\n\n### 3.1 Banco de Dados em Memória (`lib/database/pessoasDb.ts`)\n\n**Padrão**: Singleton\n\n**Características**:\n- Armazenamento com Map<id, Pessoa>\n- Índice de emails para busca rápida\n- Operações CRUD completas\n- Paginação e busca integradas\n- Thread-safe para requisições concorrentes\n\n**Métodos**:\n```typescript\n- create(data: CreatePessoaDTO): Pessoa\n- read(id: string): Pessoa | null\n- readAll(page, limit, search): PaginatedResponse\n- update(id: string, data: UpdatePessoaDTO): Pessoa\n- delete(id: string): boolean\n- emailExists(email: string, excludeId?): boolean\n- count(): number\n- clear(): void\n```\n\n### 3.2 Validação (`lib/validation/pessoasValidator.ts`)\n\n**Características**:\n- Validações reutilizáveis cliente/servidor\n- Mensagens de erro localizadas em português\n- Validação de campos individuais e compostos\n- Suporte a validação parcial (updates)\n\n**Funções**:\n```typescript\n- validateNome(nome: string)\n- validateEmail(email: string)\n- validateTelefone(telefone?: string)\n- validateDataNascimento(data?: string)\n- validateCreatePessoa(data: unknown)\n- validateUpdatePessoa(data: unknown)\n```\n\n### 3.3 API Routes\n\n#### POST /api/pessoas\n- Cria nova pessoa\n- Valida dados\n- Verifica email duplicado\n- Retorna 201 com pessoa criada\n\n#### GET /api/pessoas\n- Lista pessoas com paginação\n- Suporta busca por nome/email\n- Retorna dados paginados\n\n#### GET /api/pessoas/:id\n- Retorna pessoa específica\n- 404 se não encontrada\n\n#### PUT /api/pessoas/:id\n- Atualiza pessoa\n- Validação parcial\n- Verifica conflito de email\n\n#### DELETE /api/pessoas/:id\n- Deleta pessoa\n- Retorna 204 No Content\n\n### 3.4 Componentes React\n\n#### PessoaForm\n- Formulário reutilizável para criar/editar\n- Validação em tempo real\n- Feedback de erros\n- Suporte a loading state\n\n#### PessoasList\n- Tabela com paginação\n- Busca integrada\n- Ações (Ver, Editar, Deletar)\n- Modal de confirmação\n\n#### Páginas\n- `/pessoas` - Lista\n- `/pessoas/novo` - Criar\n- `/pessoas/:id` - Detalhes\n- `/pessoas/:id/editar` - Editar\n\n## 4. Decisões de Design\n\n### 4.1 In-Memory Database\n\n**Decisão**: Usar Map com índice de emails\n\n**Justificativa**:\n- Performance O(1) para leitura/escrita\n- Índice para busca rápida de duplicatas\n- Simples e sem dependências externas\n- Adequado para desenvolvimento/demo\n\n**Trade-offs**:\n- Dados perdidos ao reiniciar\n- Limitado pela RAM\n- Não funciona em múltiplas instâncias\n\n### 4.2 Email Normalization\n\n**Decisão**: Normalizar emails para lowercase\n\n**Justificativa**:\n- RFC 5321: local part é case-sensitive, mas na prática trata-se como insensível\n- Evita confusão do usuário\n- Padrão da indústria\n\n### 4.3 Validação Compartilhada\n\n**Decisão**: Validação em `lib/validation/` reutilizável\n\n**Justificativa**:\n- DRY (Don't Repeat Yourself)\n- Consistência entre cliente e servidor\n- Fácil manutenção\n- Segurança (validação no servidor)\n\n### 4.4 Paginação Server-Side\n\n**Decisão**: Implementar paginação no servidor\n\n**Justificativa**:\n- Escalável para grandes datasets\n- Padrão RESTful\n- Reduz transferência de dados\n- Fácil migração para BD real\n\n### 4.5 Hard Delete\n\n**Decisão**: Deletar permanentemente (hard delete)\n\n**Justificativa**:\n- Simplicidade\n- Sem necessidade de audit trail\n- Adequado para desenvolvimento\n\n**Futuro**: Implementar soft delete se necessário\n\n## 5. Fluxos de Dados\n\n### 5.1 Criar Pessoa\n\n```\nForm Submit\n    ↓\nClient Validation\n    ↓\nPOST /api/pessoas\n    ↓\nServer Validation\n    ↓\nCheck Email Duplicate\n    ↓\nCreate in Database\n    ↓\nReturn 201 + Pessoa\n    ↓\nRedirect to List\n```\n\n### 5.2 Listar Pessoas\n\n```\nGET /api/pessoas?page=1&limit=10&search=...\n    ↓\nFilter by Search\n    ↓\nSort by createdAt (DESC)\n    ↓\nPaginate\n    ↓\nReturn PaginatedResponse\n    ↓\nRender Table\n```\n\n### 5.3 Atualizar Pessoa\n\n```\nForm Submit\n    ↓\nClient Validation\n    ↓\nPUT /api/pessoas/:id\n    ↓\nCheck Exists\n    ↓\nServer Validation\n    ↓\nCheck Email Conflict\n    ↓\nUpdate in Database\n    ↓\nReturn 200 + Updated Pessoa\n    ↓\nRedirect to Detail\n```\n\n## 6. Tratamento de Erros\n\n### 6.1 Resposta de Erro Padrão\n\n```json\n{\n  \"status\": 400,\n  \"message\": \"Validação falhou\",\n  \"details\": {\n    \"nome\": \"Nome deve ter no mínimo 3 caracteres\",\n    \"email\": \"Email inválido\"\n  },\n  \"timestamp\": \"2024-01-15T10:30:00Z\"\n}\n```\n\n### 6.2 Códigos HTTP\n\n- `201 Created`: Pessoa criada\n- `200 OK`: Sucesso (GET, PUT)\n- `204 No Content`: Deletado\n- `400 Bad Request`: Validação falhou\n- `404 Not Found`: Recurso não existe\n- `409 Conflict`: Email duplicado\n- `500 Internal Server Error`: Erro do servidor\n\n## 7. Validações\n\n### 7.1 Nome\n- Obrigatório\n- 3-255 caracteres\n- Trimmed\n\n### 7.2 Email\n- Obrigatório\n- Formato válido (regex)\n- Único (case-insensitive)\n- Normalizado para lowercase\n\n### 7.3 Telefone\n- Opcional\n- 10-15 dígitos\n- Aceita formatação\n\n### 7.4 Data de Nascimento\n- Opcional\n- ISO 8601 (YYYY-MM-DD)\n- No passado\n\n## 8. Performance\n\n### 8.1 Otimizações\n\n- **Map para Storage**: O(1) acesso\n- **Email Index**: O(1) busca de duplicatas\n- **Paginação**: Apenas dados necessários\n- **Busca**: Filtro eficiente\n- **CSS Modules**: Estilos isolados\n\n### 8.2 Limites\n\n- Máximo 100 itens por página\n- Limite de memória do servidor\n- Sem cache (cada requisição recalcula)\n\n## 9. Segurança\n\n### 9.1 Validação\n- ✅ Servidor valida todas as requisições\n- ✅ Não confia apenas em validação cliente\n- ✅ Mensagens de erro genéricas em produção\n\n### 9.2 Normalização\n- ✅ Emails normalizados (lowercase)\n- ✅ Strings trimmed\n- ✅ Sem injeção de código\n\n### 9.3 Type Safety\n- ✅ TypeScript em toda a aplicação\n- ✅ Tipos para requisições/respostas\n- ✅ Validação em tempo de compilação\n\n## 10. Testes\n\n### 10.1 Cobertura\n\n- **Validação**: Todas as regras testadas\n- **Database**: CRUD completo\n- **Paginação**: Casos normais e edge\n- **Erros**: Casos de erro\n\n### 10.2 Executar Testes\n\n```bash\nnpm test\nnpm run test:watch\nnpm test -- --coverage\n```\n\n## 11. Deployment\n\n### 11.1 Build\n\n```bash\nnpm run build\nnpm start\n```\n\n### 11.2 Variáveis de Ambiente\n\nNenhuma variável obrigatória para desenvolvimento.\n\nPara produção, considere:\n- `NODE_ENV=production`\n- `NEXT_PUBLIC_API_URL` (se necessário)\n\n## 12. Limitações Conhecidas\n\n1. **Dados Voláteis**: Perdidos ao reiniciar\n2. **Single Instance**: Não funciona em cluster\n3. **Sem Persistência**: Sem backup\n4. **Limite de Memória**: Limitado pela RAM\n5. **Sem Autenticação**: Acesso público\n6. **Sem Autorização**: Sem controle de acesso\n\n## 13.
